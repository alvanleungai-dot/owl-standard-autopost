## ▶ Session 2026-06-28 — monitoring fix + INFRASTRUCTURE SELF-HEAL ⭐ READ FIRST

**TL;DR.** Two production monitoring bugs surfaced (a fake daily Telegram "task failed" alert + console
windows popping up). Root cause: `SCE-Gatekeeper` was registered with a mis-quoted `cmd` action — node never
ran → exit `0x1` with an empty log → `SCE-TaskHealth` fired a daily failure alert and the **owner had to fix
it by hand**. Fixed (`d99fdb3`) and applied live. Then the deeper lesson was closed: *the self-heal layer
lived INSIDE the Gatekeeper — the very thing that was down* — so the always-on `task-health` monitor (and the
Gatekeeper, mutually) can now **auto-re-register a broken monitor task from its own committed
`register-*.ps1`**, elevated + verified + capped, touching **NO posts / accounts / money**. **Proven live**:
the Gatekeeper was deliberately broken (`0x1`) and the monitor detected → re-registered → verified it healthy
(`0x2`) with **zero human action**.

### What shipped (81/81 unit tests green)
- **`scripts/lib/infra-repair-core.mjs`** (NEW, pure, 7 tests) — the **closed registry** of which infra/monitor
  tasks may be auto-re-registered (`SCE-Gatekeeper`, `SCE-TaskHealth`) + a per-day repair cap. Safety boundary:
  a posting/generation/browser task can **never** be in it (enforced by test).
- **`scripts/task-health.mjs`** — now auto-repairs the infra class: detect a failed registry task →
  re-register from its committed script → start + verify → quiet "🔧 自動修復" note; **escalate only what it
  can't heal**. Gated by `INFRA_AUTOFIX` (default ON); max **1 repair/day/task** (idempotent re-register, then
  escalate so it never loops on a real runtime bug).
- **`scripts/lib/gatekeeper-core.mjs` + `gatekeeper.mjs`** — a crashed REGISTRY monitor (day-1) is now an
  auto-safe `reregister` plan (was agent-verify). So task-health heals a broken Gatekeeper **and** the
  Gatekeeper heals a broken task-health → **mutual healing, no single point of failure** (the exact trap that
  hid this bug).
- **`windows/register-task-health.ps1`** (NEW) + **`register-gatekeeper.ps1`** — both monitors now register
  **S4U + RunLevel Highest** (hidden, no UAC, no stored password) so they can re-register tasks unattended.
  6h cadence, offset 30 min (TaskHealth 09:00/15:00/21:00/03:00 vs Gatekeeper 08:30/14:30/20:30/02:30) so they
  interleave — if one is down at its slot, the other repairs it ~30 min later.
- Earlier same-day (`d99fdb3`): the mis-quoted-task bug fixed in `register-gatekeeper.ps1`; task-health treats
  a monitor's exit-2 as benign (still a real failure for gen/posting); all enabled SCE tasks switched to hidden
  S4U (no more console windows).

## ▶ POSTING INCIDENT + HARDENING (2026-06-22) ⭐ READ FIRST

**TL;DR.** This week's posts didn't go out. Root cause was a chain of **silent failures** across the
pipeline. The pipeline is now hardened so this class of failure **fails loudly** at every layer, and a
new monitor watches the scheduled tasks themselves. **All automated posting is FROZEN** until one
critical fix (wrong-page) is verified live.

### What broke (root causes — all confirmed)
1. **Better Life W26 generated broken.** During the 06-18 API-credit outage, all 5 posters failed to
   render. `gen-week` swallowed the per-poster failures and **exited 0**, so `BetterLife-WeeklyAutopilot`
   reported success (`0x0`) on an all-broken week. (TML's gen crashes hard → it correctly reported `0x1`.)
2. **Auto-approve rubber-stamped the broken posts.** `review-core.planSweep` had no validity check, so
   the 48h timer flipped 5 `failed` posts to `approved`.
3. **The scheduler crashed silently.** `better-life/schedule-week.mjs` did `keyboard.type(undefined)` on
   the missing caption → uncaught crash → `BetterLife-AutoSchedule` exited `0x1`. **No alert, no log.**
   `TML-AutoSchedule` also exited `0x1` (its own cause, below). Nothing told the owner.
4. **🔴 CRITICAL — wrong-page.** The TML scheduler composes into whatever page the Chrome profile last
   defaulted to (it was defaulting to **Sunmood**). It never pins TM Health → risk of posting one
   brand's content to a sister brand's page. Also the photo button selector (`/^Add photo$/i`) is stale
   (the composer now uses an icon row) → attach fails → commit crash.
5. **The watchdog is reactive.** It only notices *after* a post is overdue, can't tell broken content
   from not-yet-posted, auto-fixes only TML, and **never checked the task exit codes** — so a crashed
   AutoSchedule was invisible.

### What was fixed this session (shipped + tested — 39/39 unit tests green)
- **Auto-approve guard** (`review-core.mjs` `isBroken` + `planSweep` returns a `broken[]` bucket): a
  `failed`/errored post can **never** be auto-approved again. +3 tests.
- **Broken-content alerts**: all three review bridges (`tg-bridge.mjs` ×3) fire a **deduped Telegram
  alert** when the sweep finds broken posts, instead of silently swallowing them.
- **Generation fails loudly**: `gen-week.mjs` (BL) and `sunmood/gen-week.mjs` now exit non-zero when any
  poster fails — so the autopilot task reports failure (caught by task-health/preflight).
- **Task-health monitor** (NEW): `scripts/task-health.mjs` + pure `scripts/lib/task-health-core.mjs`
  (4 tests). Reads every SCE task's `LastTaskResult` and escalates any non-zero. Registered as
  **`SCE-TaskHealth` daily 09:00** (with output logging). Verified: it caught the real
  `BetterLife-AutoSchedule 0x1`, `TML-AutoSchedule 0x1`, `TML-WeeklyAutopilot 0x1`, `SCE-Preflight 0x2`.
- **Task output logging**: `BetterLife/TML-AutoSchedule` + `-WeeklyAutopilot` now redirect stdout/stderr
  to `logs/<task>.log` (triggers preserved) — failures stop being traceless.
- **POSTING FREEZE** (`secrets/POSTING_FROZEN` sentinel + guard in both `schedule-week.mjs`): every real
  commit — AutoSchedule tasks **and** the watchdog's auto-republish — is blocked while the file exists.
  `--dry` still works. Verified both schedulers refuse to post in real mode.

### 3. Topic engine rebuilt — structurally non-repeating ✅
`scripts/lib/topic-engine.mjs` upgraded from "diverse rotating lenses" to a **structural never-repeat** system, fixing the
repetition the owner flagged:
- **Combinatorial axes:** every search is **(lens × persona × angle) = 32 × 16 × 10 ≈ 5,120 cells**, each yielding several
  web-mined topics → effectively endless.
- **Coverage map** (`companies/<brand>/topic-coverage.json`): tracks lens/persona/angle usage and deliberately mines the
  **least-covered** cells each run, so non-repetition is **structural, not hoped-for**.
- **Semantic dedup:** OpenAI `text-embedding-3-small` rejects **paraphrase-level** repeats (如何保護子女 vs 點樣保護子女)
  that string-matching missed; graceful fallback to the substring filter with no key/network.
